# 合并分支

## 边界

- 目标分支默认 `test`，用户明确指定时可以是别的分支。
- **master / main 系列一律拒绝**（含 `master-xxx`、`master_xxx`、`main` 等变体）：
  合进主干等于上线，必须到 GitLab 网页端人工创建 MR 走审核，不在这里代劳。
  用户坚持时也不绕道——不要改用 `glab` 直调、也不要手工 `git merge` 后推送。
- 推送和合并都收不回：执行前必须把完整计划一次说清并取得确认，不允许边做边问。
- 不修改任何代码，不解决冲突，不变基，不 `git commit --amend`，不强制推送。
- 不擅自决定提交范围。有未提交改动时列出来问用户，不自动 `git add`。
- 不泄露 Token、Cookie、`.env` 内容或完整的认证响应。
- 全流程失败时如实报告卡在哪一步、哪些动作已经生效，不把「已准备」说成「已完成」。

## 1. 勘察现状

先看清楚状态再决定做几步——同一句「帮我合并」，工作区不同要做的事完全不同。

```bash
git rev-parse --abbrev-ref HEAD
git status --short
git rev-parse --verify --quiet "@{upstream}" || echo "无上游"
git rev-list --count "@{upstream}..HEAD"
```

据此判断：

- 当前分支就是目标分支：直接停下说明，不能自我合并。
- 有未提交改动：进入第 2 节。
- 远端没有该分支，或本地领先远端：推送是必需步骤，写进计划。
- 工作区干净且与远端一致：只需要合并这一步，**不要反过来问用户「要不要先提交点什么」**，
  没有的事不要造。

## 2. 有未提交改动时

不要自己提交，也不要假装它们不存在。列出改动文件，让用户选：

1. 先提交再合并——交给受控 Git 提交流程处理，完成后再回到本节点；
2. 这些改动不参与本次合并——确认后继续，被留下的改动保持未提交状态；
3. 取消。

工作区混着几个不相关主题时，必须让用户先明确范围，不擅自打包。

## 3. 说明计划并取得确认

把要做的事一次列全，标出从哪一步开始不可逆，然后停下等确认。

```text
当前分支 feature/login，工作区干净，本地领先 origin/feature/login 2 个提交。

要让这段代码进 test：
1. 推送 feature/login 到 origin（2 个提交）
2. 建 MR feature/login -> test，合并，追踪流水线

第 1 步之后就收不回了。确认？
```

只需要合并时同样要说明，但可以简短——用户已经明确要求合并，不必为一步动作反复确认。

## 4. 执行

### 4.1 推送

仅在计划里包含且用户已确认时执行：

```bash
git push -u origin <当前分支>
```

推送失败（无权限、远端有新提交需要先拉取等）时停下报告，不自动 `--force`，
不自动 `git pull` 改变本地历史。

### 4.2 合并

```bash
sw merge
```

指定源分支时用 `sw merge <分支>`，换目标分支时加 `--target <分支>`（master / main
系列会被命令直接拒绝，这是最后一道闸，不要试图绕过）。
这条命令自己会打印源分支、目标分支和 MR 地址，
然后完成建 MR、等可合并、合并、追踪流水线全过程，中断后重跑会按 GitLab 上的真实
状态继续，不会重复建 MR 或重复合并。

命令不存在时说明 `sw` 随 SpecWeaver App 分发，请确认已安装；缺 `glab` 或 `jq` 时
按它给出的提示安装，不要绕过它自己去调 GitLab API。

按退出码处理：

- 退出码 0：合并完成，流水线通过或明确跳过，进入第 5 节。
- 冲突：命令会停在合并前。转告用户冲突需要人工解决，解决并推送后重跑本 Skill 即可
  从当前状态继续。**不要尝试自动解决冲突。**
- 流水线失败或取消：合并**已经生效**，必须明确说明这一点，再给出流水线地址。
  不要暗示可以「重跑合并」——代码已经在 test 上了，要处理的是流水线本身。
- 其他失败：原样转达命令的错误输出和它给的下一步建议，不自行推测原因。

## 5. 报告与后续提示

报告实际结果：源分支、目标分支、MR 地址、合并提交、流水线地址与最终状态。
没拿到的信息如实说没拿到，不要用「应该已经」这类措辞。

然后**按下列条件输出提示文案**。这一节是要对用户说的话，不是要执行的步骤——
列出来的事情一律等用户开口再做：

- 存在关联 Tower 链接，且该链接下还没有本次分支与 HEAD 的同步记录时：
  提示可以把开发信息同步到 Tower。
- 存在关联 Tower 链接时：提示可以把这次改动记进今天的日报。

没有关联 Tower 就两条都不提，报告完结束。不要为了决定提不提示而追问用户
「这次改动关联哪个 Tower」——只用流程中已经确认下来的链接。

提示形如：

```text
合并完成：feature/login -> test，流水线 #555 通过

还可以帮你做：
- 把分支和提交同步到关联的 Tower 任务
- 把这次改动记进今天的日报

说一声就行。
```
