# 日报整理

## 边界

- 只在用户明确要求记录或汇总日报时运行；不能在每次对话结束时自动写入。
- 只记录当前对话中有完成证据的事项。计划、讨论结论、尝试失败和待办不算完成。
- **只记录落到代码上的产出**：改了哪些模块、新增了哪些组件、实现了什么功能。
  需求收集、资料整理、调研这类开工前的准备工作不进日报。
- 日志默认按天保存到 `~/.specweaver/daily-logs/YYYY-MM-DD.md`；设置
  `SPECWEAVER_HOME` 时改用该目录下的 `daily-logs/`。
- 只保存项目名称、需求名称和完成事项，不保存对话全文、私有链接、Cookie、密码、Token、账号或登录响应。
- 记录动作只写本机共享日志，不修改当前项目代码，不执行 Git 提交或外部发布。

## 判断用户意图

按用户当前表达选择一种模式：

1. “整理一下日报”“记录这次完成内容”“加入日报”：执行“记录本次任务”。
2. “整理今天日报”“汇总今日工作”“生成今天的日报”：执行“汇总当天日报”。
3. 用户同时要求先记录本次任务再汇总今天：先记录，再汇总。

无法判断目标日期时使用本机当天日期。用户明确指定日期时使用该日期，不擅自跨天合并。

## 记录本次任务

1. 按“对话中明确的产品或项目名 → 当前任务所在目录 → 仓库名”的优先级确定项目
   名称。多项目仓库不能直接使用仓库名；无法唯一判断时先询问用户。
2. 确定这批完成事项所属的需求：优先用 Tower 任务标题，没有就用能概括这批改动的
   功能名。一次对话涉及多个需求时按需求分多次执行脚本，不要塞进同一个需求。
3. 提取当前对话中已经完成并经过验证的结果，写清**改了哪些模块、新增了哪些组件、
   实现了什么功能**，每条都要能独立看懂。
4. **准备性工作不写**：需求收集、资料整理、蓝湖与 Eolink 取数、调研结论、
   生成 requirement.md、读代码确认可行性——这些是开工前的准备，不是当天产出。
5. 合并语义重复的事项；不要记录执行过程、命令流水或泛泛的“完成开发”。
6. 检查内容中没有认证信息、私有链接和原始响应。
7. 从插件根目录执行：

```bash
python3 skills/daily-report/scripts/daily_log.py add \
  --project "<项目名称>" \
  --requirement "<需求名称>" \
  --completed "<完成事项 1>" \
  --completed "<完成事项 2>"
```

如果当前工作目录不是插件根目录，使用脚本的绝对路径。脚本每天创建一个 Markdown
文件，按“项目 → 需求”两级合并，同一需求下完全相同的完成事项不会重复写入。

8. 向用户报告实际写入的项目、需求、事项数量和日志绝对路径。没有完成事项时不写文件，说明原因。

## 汇总当天日报

1. 执行：

```bash
python3 skills/daily-report/scripts/daily_log.py show
```

指定日期时追加 `--date YYYY-MM-DD`。脚本只读取当天对应的 Markdown 文件。

2. **脚本的标准输出已经是可直接发送的成品，原样转述，不要改写、重新排版或补充**：

```text
### 项目名称
1.需求名称
1.1 完成事项
1.2 完成事项
2.另一个需求
2.1 完成事项
```

编号由脚本按存储顺序生成。日报正文只有这些内容，文件路径这类提示走标准错误，不要带进去。

3. 不把汇总结果再次追加到共享日志。当天没有记录时明确说明，不虚构内容。

## 完成检查

- 日期、项目名称和需求名称明确；
- 每一项都能在当前对话或当天共享日志中找到完成证据；
- 写的是模块、组件、功能这类代码产出，没有混入需求收集、调研等准备工作；
- 没有混入进行中事项、问题、明日计划或敏感信息；
- 记录模式已确认文件真实写入，汇总模式已覆盖当天全部项目且输出原样来自脚本；
- 明确提醒边界：没有主动说“整理一下日报”的任务不会自动进入日志。
