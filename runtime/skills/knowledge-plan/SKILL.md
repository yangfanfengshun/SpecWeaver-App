# 查知识库，必要时写开发计划

先分清你是谁，再干活。

## 你是主对话 Agent 时

用户刚在本对话把需求聊清楚，再说要对照知识库准备开发，例如「写开发计划」「按现有规范出计划」「先看项目里怎么写再开发」「摸下知识库准备开发」：

1. **不要自己读** `.knowledge` 原文，不要自己写 `dev-plan.md`（长对话再灌库会把上下文撑爆）
2. **立刻派一次** Subagent（Cursor 用 Task；Codex 用一次子 Agent 调用）。不要连续派多个
3. 给子 Agent 的说明里写清：
   - 你是计划 Subagent，遵循本 Skill 后半段，**禁止再派 Subagent**
   - 需求：有 `requirement.md` 给路径；没有就把本对话需求**压缩成一段摘要**带上（不要贴整段闲聊）
   - 写出与需求文件同目录（或仓库根）的 `dev-plan.md` 五节
4. 子 Agent 返回后：把「不明确」问用户；计划不对再派一次，带上哪里错了

用户只是问项目里某能力怎么写、查一下知识库，没说要开发：可以在本对话快速查，不必派。

## 你已经是 Subagent 时

直接从下面「边界」开始干活，禁止再派 Subagent。

## 边界

- 不修改 `src/` 等业务代码，不改 `.knowledge/`，不 `git add`、不提交
- 不重写需求分析，不发明接口字段
- 需求来源按有什么用什么：`requirement.md` → 主 Agent 给的摘要 → 当前对话。不要因为没有分析 md 就停工
- 作为 Subagent 被派来准备开发：必须写出五节 `dev-plan.md`。拿不准的进「不明确」，不要写成步骤，不要追问用户
- 主对话里只查库：查完回答命中卡片、何时用、硬约束、原文路径即可，不必写计划文件

## 1. 定位仓库

1. 当前 Git 仓库根（向上找 `.git`）。有 `requirement.md` 时从它所在仓库找。`src` 可能在 `client/` 等子目录，`.knowledge` 仍在 Git 根。
2. 知识库路径：`<git根>/.knowledge/`
3. 本 Skill 的查询脚本：与本 `SKILL.md` 同级的 `scripts/query.py`

## 2. 查知识库

有 `.knowledge/catalog-stack.json` 时：

1. **先读** `catalog-stack.json` 和 `catalog-project.json`（只读这两份菜单，不要把 `stack/`、`project/` 全文灌进来）
2. 对照需求（`requirement.md`、主 Agent 摘要、或当前对话），从 catalog 里**勾库中已有的 tag**（用户语言 + 组件名）。勾不上的记下来，后面摸代码或写入不明确
3. 用脚本精确命中，不要把需求整句当 tag：

```bash
python3 <本Skill目录>/scripts/query.py --cwd <git根> <tag1> <tag2> ...
```

默认 JSON。`status` 为 `no_knowledge` / `incomplete` 时当没库处理。只返回元数据和 `source` 路径，**不要让脚本读原文**。

4. 按命中的 `source` **按需 Read 那几篇** md，再按 `paths` 打开关键代码核对。不要把未命中的卡片读进来。

没有 `.knowledge`：跳过 2，整段改成摸与需求相关的代码。摸不清写「不明确」，不许空编。

只查库且你在主对话：把命中摘要告诉用户，按需打开一两篇原文核对。到此可以结束。不要在主对话把 stack/project 全文读完。

## 3. 写计划（Subagent 准备开发时必走）

写到 `requirement.md` 同目录；没有分析 md 就写到仓库根。文件名 `dev-plan.md`。第一版颗粒要细，能按步骤动手；写代码时仍应按「引用」打开原文，不能只盯子弹。

固定五节，标题用下面这些：

```markdown
# 开发计划

## 步骤
## 复用
## 硬约束
## 引用
## 不明确
```

### 步骤

按开发顺序。每一步落到文件/目录、干什么、跟哪套现成写法走（点名可抄的页面）。

不合格：`改订单列表`  
合格：`在 src/components/_pages/order 的待处理 Tab 按 ProTableExtend + formatTableRequest 加一列，对标 _pages/order 现有列表，不要新起裸 ProTable`

禁止把「不明确」里的猜测写成步骤。

### 复用

命中的卡片 `id` + 本仓库可以对标的实现路径。没库就写对标到的代码路径。

### 硬约束

从命中卡片的 `constraints` 和原文里的硬约束**抄原文几句**进来。不要只写「见 table.md」。

### 引用

供主 Agent 核对，不贴说明书全文：

- 卡片 id
- 原文路径（如 `.knowledge/stack/table.md`）
- 关键代码路径

### 不明确

知识库没有、代码摸不清、和需求冲突的。单独一节。没有就写「无」。

## 4. 结束

只查库：列出命中的卡片 id 和原文路径即可。

写了计划则再返回：

- `dev-plan.md` 的绝对路径
- 命中了哪些卡片 id（或「无知识库，已摸代码」）
- 「不明确」是否非空（非空则先问用户，不要直接开工）
