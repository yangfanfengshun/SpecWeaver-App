# 把本轮开发沉淀进知识库

在**当前会话**里根据已经发生的开发归纳变更，直接改 `.knowledge/`。不要派 Subagent——证据就在这轮对话里。

## 边界

- 只改当前 Git 仓库根的 `.knowledge/`，不修改 `src/` 等业务代码。
- 只处理**本轮任务**相关的卡。禁止全仓重扫、禁止当 `spec-knowledge-init` 用。
- 直接落盘，写完再报告。不要先列清单等用户点头。
- 没有 `.knowledge/`：停，让用户先跑 `spec-knowledge-init`。
- 抽不出证据的事实不写卡；标「待确认」或跳过。
- 未经用户明确要求，不 `git add`、不提交。用户接着要提交时，先写完知识再转交 `spec-git-commit`。
- 不删卡，除非入口确实没了且用户要求删。

## 判断用户意图

1. 明确说更新 / 沉淀 / 纠偏 / 入库 / 把这次写进知识库：执行。
2. 本轮开发已收尾（做完了、可以提交了、这个需求完成了），且对话里已有可入库事实：执行，不必再问要不要写。
3. 用户明确说先别改知识库：停。
4. 归纳后既无纠偏也无新增：不改文件，报告「本轮无需更新」。

## 1. 确认仓库和库

1. 当前 Git 仓库根（向上找 `.git`）。`src` 若在子目录，`.knowledge` 仍在 Git 根。
2. 必须已有 `.knowledge/catalog-stack.json`。缺库或残缺当没库处理。
3. 确保 `.knowledge/` 未被 `.gitignore` 忽略。

## 2. 从本轮会话归纳变更

按这个顺序取证，能定位就停，不要把整库灌进来：

1. **当前对话**：改了哪些模块、新入口/新封装、开发中发现哪张卡写错了。
2. 本轮 `git diff`（含已提交未推送的，若用户指的是刚做完的那批）。
3. 若本轮用过开发计划，可读缓存 `~/.specweaver/cache/knowledge-plan/<仓库名>/dev-plan.md` 的「不明确」——当时的缺口现在可能已有答案。设置了 `SPECWEAVER_HOME` 时改用该目录下的同名路径。

每条事实归到三类，没有证据的不进前两类：

| 类 | 何时 | 做什么 |
| --- | --- | --- |
| 纠偏 | 已有卡的路径、组件名、硬约束、何时用、现状与本轮代码不符 | 改对应 md，并同步 catalog 里变了的字段 |
| 新增 | 本轮落地了新入口、新封装或新模块，catalog 里没有对应卡 | 写 md，登记进对应 catalog |
| 不入库 | 这一单需求的 F-01 / 验收、一次性修补、猜的接口字段、官网教程 | 结束报告里写原因，不写卡 |

同一业务 tag 尽量只出现在一张卡上。新卡的 `id` / `name` / 文件名跟**本仓库**走，不要抄别的端。

## 3. 只读相关卡

1. 先读 `catalog-stack.json` 和 `catalog-project.json`（只读菜单）。
2. 只打开本轮要动的那几篇 md，按 `paths` 打开关键代码核对。不要把未涉及的卡片读进来。
3. 不确定卡在哪时，用计划 Skill 的查询脚本做 tag 精确命中：

```bash
python3 <本Skill目录>/../knowledge-plan/scripts/query.py --cwd <git根> <tag1> <tag2> ...
```

只返回元数据和 `source`，不要让脚本读原文。

4. 新增业务入口且拿不准路由表是否多了行时，可跑 `knowledge-init` 的 `scripts/inventory.py`。默认不跑。脚本不写库。

## 4. 直接写入

卡片字段、md 结构和 init 同一套。catalog 与 md 必须一起改，没有原文不许登记。

```json
{
  "id": "table",
  "name": "分页表格",
  "tags": ["列表", "分页", "ProTableExtend"],
  "use_when": "何时用",
  "use_when_not": "何时不用",
  "source": ".knowledge/stack/table.md",
  "paths": ["src/..."],
  "constraints": ["必须遵守的禁区"]
}
```

`constraints` **只放硬约束**。主流写法、历史例外、待确认、相对时间放 md 正文并打标，不要升级进 JSON。

新卡 md 用这个短结构；纠偏只改本轮证伪的章节，不要整篇重写：

```markdown
# 名称

## 何时用 / 何时不用
## 路径
## 硬约束
## 现状与例外
## 待确认
## 证据
```

`证据` 写清本轮读了哪个文件。底座新卡至少：定义文件 + 一处真实业务引用。

- 纠偏：按 `id` 改 catalog 里变了的字段，并改对应 md。
- 新增：md 放到 `stack/` 或 `project/`，`source` 指向它，追加进对应 catalog 的 `cards`。`id` 不与已有卡重复。
- JSON 保持可解析；不要重排无关卡片。

## 5. 验收

写完立刻核：

- catalog JSON 能解析；`id` 不重复；每张动过的卡有 md；`source` / `paths` 存在
- `constraints` 里没有推断和相对时间
- 没动本轮无关的卡

不通过就补，再报告。

## 6. 结束时报告

- 纠偏了哪些卡片 `id`，各改了什么
- 新建了哪些 `id`（stack 还是 project）
- 跳过 / 不入库的条目和原因
- 标了待确认的条目
- 未暂存、未提交。若用户还要提交，转交 `spec-git-commit`
