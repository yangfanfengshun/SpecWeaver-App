# 四件套

用户说「四件套」就是同时明确要求这四步。按顺序做完，不要改成菜单让用户再确认一遍。

1. 提交
2. 评论 Tower
3. 记录日报
4. 合并到 test

某一步必须问用户时，问完再继续，不要把后面的步骤丢掉。提交范围里有多个独立主题，或对不上唯一的 Tower 链接时，先问，得到答案再往下。

不包含知识库沉淀。不要转交 `spec-knowledge-update`，也不要再提。

## 提交和评论

读取并遵守 `spec-git-commit` 的第 1–5 节。第 6 节整节不做。

工作区没有要提交的改动时，不造空提交，用当前分支的 HEAD 做第 5 节。用户说明这次没有 Tower 时，跳过评论，继续日报和合并。

评论只有返回 `status` 为 `success` 才算发出。认证失效时说明评论没发出，保留已完成的提交，日报和合并继续；认证恢复后只补评论。

## 日报

读取并遵守 `spec-daily-report` 的「记录本次任务」。不要汇总当天日报。

纯视觉微调，或没有落到代码上的概念时，跳过这一步，向用户说明没记，然后继续合并。

## 合并

读取并遵守 `spec-git-merge`。这一步放在最后：终端里的命令一启动，本 Skill 结束。不要读终端，不要再补日报或评论。

远端是 GitHub，或看不出是 GitLab 时，前三步照做，合并停下并说明原因。

## 怎么收尾

合并已经启动时，只说命令已在终端启动。评论和日报的结果在这之前已经分别报告过。

没走到合并时，说明停在哪一步、已经完成什么。
